# Repository Rules & Constraints

## Architecture & Code Organization
- **[AVOID]** Global ambient `.d.ts` namespaces (`NDataProvider`, `NCloudData`, etc.) in `src/interfaces/` for domain-specific types — Colocate page types directly in page-level `types.ts` to improve IntelliSense discoverability, eliminate dead types, and maintain clean domain boundaries. Keep only global core interfaces (`Abstract`, `NBaseApi`, `auth`, `custom-component`) in `src/interfaces/`.
- **[NEVER]** Scatter domain entity type ownership across multiple arbitrary files — Entity contracts must be canonically owned and exported by their primary managing page (`types.ts`), with secondary pages cleanly importing directly from the owning page.
- **[AVOID]** Manual defensive envelope unpacking (`res?.data?.data`) inside UI page hooks — Always rely on custom API hooks (`useCustomOne`, `useCustomList`, `useCustomData`) built-in unwrapped `data` accessor and use the `transform` callback prop when domain-specific fallbacks or projections are required.
- **[AVOID]** Hardcoding raw API endpoint strings or directly reading `process.env.NEXT_PUBLIC_*` in components, hooks, or pages — Always import typed endpoint paths and environment configuration from `@/config` (`API_ENDPOINT`, `env`) to maintain single-source-of-truth contracts.
- **[NEVER]** Access `window` or browser DOM APIs during initial SSR render in custom hooks without guards — Always guard browser-only APIs (`window.matchMedia`, `localStorage`) with `typeof window !== 'undefined'` or run them inside `useEffect` to prevent Next.js hydration mismatches.
- **[PREFER]** Relative imports (`../types`, `../constants`, `../utils`, `../hooks`) for intra-page colocation within `src/app/**` to maintain self-contained modules, prevent brittle path rewrites during route restructuring, and improve code readability. Use absolute alias `@/...` for global cross-module packages (`@/components/custom-antd`, `@/hooks`, `@/enums`, `@/libs`, `@/config`).
- **[NEVER]** Hardcode raw string resource paths in `<ListTable deleteResource="..." />` or Refine hook configurations — Always import and use centralized `RESOURCE.<NAME>` constants from `@/config`.
- **[AVOID]** Writing inline slugification / string sanitization logic in components — Use the centralized `slugify` utility from `@/libs`.
- **[PREFER]** Built-in `FormRuleType` validators (`FormRuleType.Code`, `FormRuleType.Url`, `FormRuleType.Required`, `FormRuleType.Email`, `FormRuleType.Length`) via `buildFormRules` over hand-crafted inline regex or ad-hoc custom validators in modal forms.
- **[NEVER]** Re-export `utils` from `constants.ts` (e.g. `export * from './utils'`) when `utils` or its components import `constants` — Avoid circular module references that break Turbopack/Next.js bundle evaluation. Keep `constants.ts` and `utils/` decoupled.
- **[AVOID]** Hardcoding raw service options or checking raw string values (`service === ...`) across multiple JSX components — Use centralized metadata maps (`SCRAPER_SERVICE_METADATA`) and capability helpers (`checkService`) for capability-driven UI rendering.
- **[PREFER]** Colocating shared domain assets (components, hooks, enums, utils, types, constants) directly at the module root (`src/app/(root)/scraping/features/`) and splitting enums into single-responsibility files (`*.enum.ts`) with barrel export (`index.ts`). Keep dynamic route segments (`[dataProviderId]/`) strictly for Next.js route pages (`page.tsx`).
- **[AVOID]** Monolithic type files mixing multiple domain entities or dead types — Modularize types into object-centric files (`data-provider-feature.types.ts`, `config-version.types.ts`, `target-config.types.ts`, `form.types.ts`) with a unified barrel export (`index.ts`) matching backend entity and DTO boundaries.
- **[AVOID]** Defining flat, unstructured configuration interfaces with 20+ mixed properties — Group complex configurations (`ITargetConfig`) into cohesive sub-interfaces (`ITargetConfigLimits`, `ITargetConfigNetwork`, `ITargetConfigSelectors`, `ITargetConfigEngine`, `ITargetConfigGenerators`).

## UI/UX & Component Patterns
- **[NEVER]** Overload main entity list tables with multi-feature configurations and obsolete action columns — Keep table rows focused on core identity fields (name, code, status, created date) and navigate to dedicated feature dashboards (`/scraping/features/:dataProviderId`) for detailed configurations.
- **[AVOID]** Multi-step create-then-configure modal flows when initializing features or sub-resources — Use direct 1-step configuration modals with draft state that automatically perform initialization (`POST`) or update (`PUT`) upon submission.
- **[AVOID]** Navigating away to separate pages for fast sandbox testing and version rollbacks — Keep testing playgrounds and version history inspector inside focused modal tabs to preserve parent page context.
- **[AVOID]** Using raw HTML tags (`div`, `span`, `h1`, `p`) with verbose ad-hoc Tailwind classes when equivalent `custom-antd` components (`CustomRow`, `CustomCol`, `CustomFlex`, `CustomSpace`, `CustomTypography`, `CustomCard`, `CustomButton`, etc.) exist — Prefer Ant Design primitives to ensure seamless theme token integration and consistent component hierarchy.
- **[PREFER]** Modal-level tabs ('config' | 'test') with pre-flight cross-tab validation for wide playground configuration and dedicated sandbox testing over cramped 2-column split screen layouts.
- **[AVOID]** Triggering feature test runners without cross-form validation — Validate both the configuration form (e.g. required selectors, URL patterns, script templates) and test input form before dispatching test requests.
- **[AVOID]** Exposing obsolete test mode switches or hardcoding query requirements when query placeholders are not configured — Synchronize test input requirements dynamically with active form configuration (`queryPlaceholder`).
- **[AVOID]** Reusing scraping function generator templates for search features — Provide dedicated default search templates for both HTML and API scraper service types.
- **[AVOID]** Enabling experimental `reactCompiler: true` during active development without native Rust compiler support — React Compiler triggers fallback Node.js Babel AST transformation on initial on-demand route compilation in Turbopack, causing significant route transition latency.
- **[AVOID]** Duplicating shared form sections (e.g. Limits, Advanced switches, Change Log) across scraping and search configuration forms — Extract modular shared components (`FeatureLimitsSection`, `FeatureAdvancedSection`, `FeatureChangeLogSection`, `FeatureCodeSection`) to maintain consistent form state and schema synchronization.
- **[AVOID]** Duplicating form lifecycle initialization (`useEffect` mapping) and mutation save logic across feature configuration forms — Use the centralized `useFeatureConfigForm` hook and `extractTargetConfigFromFormValues` transformer.
- **[AVOID]** Reading raw form field values in test runners without parsing stringified JSON fields (`headers`, `cookies`) — Always process form values through `extractTargetConfigFromFormValues` before dispatching test runner requests.
- **[AVOID]** Placing mutation change log notes at the bottom of lengthy scrollable configuration forms — Colocate change description inputs in the modal footer or dedicated inspection panel to streamline verification and submission workflows.
- **[NEVER]** Omit mandatory form validation on version change descriptions (`changeDescription`) when backend DTO requires it — Enforce required rules on change log fields to match backend schema contracts.
- **[AVOID]** Exposing browser HTML sandbox testing mode (`CustomSegmented` HTML mode) for HTTP API or Local Folder scrapers — Only allow URL/Query testing for non-browser engines to avoid invalid simulation states.
- **[AVOID]** Retaining orphaned legacy form section components after extracting unified shared form components — Purge obsolete components (`ScrapingAdvancedSection.tsx`, `ScrapingCodeSection.tsx`, `ScrapingLimitsSection.tsx`, `SearchCodeSection.tsx`) immediately to avoid confusing future maintenance.
- **[AVOID]** Using `any` type in form submit handlers, test runner hooks, and test result displays — Enforce strict typing (`TestInputFormValues`, `FeatureTestResult`) across all form and test flows.
- **[AVOID]** Rendering long, unstructured configuration forms without visual grouping — Organize form sections visually into clear thematic clusters with distinct headers and badge icons.
- **[NEVER]** Call async mutation functions inside `try { fn() } finally { setLoading(false) }` blocks without `await` — The `finally` block executes synchronously in the same microtask tick, resetting the loading state before the asynchronous operation completes.
- **[AVOID]** Omitting loading and disabled states on async mutation triggers (e.g. status switch toggles, form submissions, version rollbacks) — Ensure interactive triggers track loading states to prevent race conditions and duplicate requests.
- **[AVOID]** Scoping loading spinners (`<CustomSpin />`) only to internal modal tabs or body sections — Wrap entire modal containers (`modalRender`) with unified loading overlays during critical async operations to prevent backdrop interaction and unintended dismissal.
- **[PREFER]** Built-in full loading overlay support directly in base modal primitives (`CustomModal` via `loading`, `spinning`, `loadingTip` props) over duplicating ad-hoc `modalRender` wrappers with custom CSS overrides in consuming modal dialogs.
- **[PREFER]** Dedicated confirmation modals with structured visual diff inspection (`CodeDisplay` / `ReactDiffViewer`) and mandatory change reason validation before submitting mutations on existing configurations over direct form saves.
- **[AVOID]** Allowing mutation of immutable engine parameters (`service`) after feature initialization — Disable `service` engine selector in edit mode and history preview to prevent breaking active parser scripts and capabilities.
- **[PREFER]** Explicit opt-in switches for complex/optional configurations (e.g. `headers`, `cookies`) over always-expanded bulky editors — Collapse optional JSON code editors behind toggle switches to reduce cognitive load and keep form layouts compact.
- **[AVOID]** Using binary switch toggles (`CustomSwitch`) for domain resources with multi-state lifecycles (e.g. `READY`, `TESTING`, `DISABLED`, `ERROR`, `UNCONFIGURED`) — Use status dropdown/select badges (`FeatureStatusSelect`) to provide explicit, controlled state transitions.
- **[AVOID]** Prop-drilling feature modal, test runner, and history state through deep component hierarchies — Encapsulate feature domain controllers in cohesive React contexts (`FeatureModalContext`, `FeatureCardContext`, `FeatureHistoryContext`, `FeatureTestContext`).
- **[AVOID]** Allowing unrestricted status transitions on UI when backend enforces a Finite State Machine (FSM) — Synchronize selectable target statuses dynamically based on the current entity status (`SELECTABLE_FEATURE_STATUS_TRANSITIONS`).
- **[AVOID]** Hardcoding field mapping in form initialization utilities (`mapConfigToBaseFormValues`) — Dynamically merge `defaultConfig` generated from form section schemas (`getDefaultFormValuesFromSections`) to ensure feature-specific fields (e.g. Search parameters) are cleanly populated.
- **[AVOID]** Overusing code diff viewers (`ReactDiffViewer` / `CodeDisplay`) for short, single-line configuration properties — Use concise structured field badges/cards (`displayNewValue`, `label`, `section`) and reserve code diff viewers strictly for multi-line scripts or complex JSON blocks.
- **[NEVER]** Omit subtype properties in form section schemas when inheriting configuration interfaces (`ISearchTargetConfig extends ITargetConfig`) — Ensure all inherited fields (e.g. `mainContentSelector`) are present in the form schema so users can configure them and default values are properly populated.
- **[AVOID]** Storing active item IDs in persistent component state during modal initialization when the default behavior is to track the latest dynamic active item — Storing an ID on mount eagerly locks the view to stale cached data and ignores incoming background query updates.
- **[NEVER]** Call `query.refetch()` inside a `useEffect` with `query` in its dependency array — The `query` object returned by TanStack Query / Refine changes reference on every fetch/state transition, triggering an infinite network request loop. Always rely on `queryOptions: { refetchOnMount: 'always' }` or `enabled: Boolean(open)` to load fresh data on modal open, and trigger `query.refetch()` only inside explicit mutation success callbacks.
- **[AVOID]** Pairing `useCustomModalForm` with raw `<CustomModal>` and `<CustomForm>` — Always use the standard `<CustomModalForm>` wrapper from `@/components/common` to guarantee automatic binding of modal footer action buttons, form reset, responsive layout, and loading states.
- **[NEVER]** Use catastrophic backtracking regex patterns like `([^"\\]|\\.)*` combined with lookahead/trailing matches (`\s*:`) for code/JSON syntax highlighters — Always use linear single-pass tokenization (`"(?:[^"\\]|\\.)*"`) and `useMemo` to prevent freezing the browser main thread.
- **[AVOID]** Rendering raw internal enum values or key strings in modal titles and tags — Always map domain keys (e.g. `service`) through centralized label dictionaries (`SCRAPER_SERVICE_LABELS`) and maintain compact, consistent modal header styling (`bodyClassName="!p-2.5 sm:!p-4"`, `className="top-6 max-w-[96vw]"`).
- **[AVOID]** Omitting configurable backend DTO request flags (e.g. `autoValidate`) in creation/mutation modal forms — Ensure form initial values and interactive toggle controls synchronize with backend schema options to preserve full user control.
- **[AVOID]** Passing nested legacy props like `modalProps={{ ... }}` to `CustomModal` or using raw Ant Design form controls in dialogs — Use atomic form controls (`CustomInputForm`, `CustomSelectInput`, `CustomSwitchForm`) and declare validation rules through `FormRuleType` / `buildFormRules`.
- **[AVOID]** Re-declaring duplicated notification, query, or transform props across custom API hooks — Inherit base contracts (`IBaseApiNotificationRequest`, `IBaseApiUrlRequest`, `IBaseApiQueryRequest`, `IBaseApiTransformRequest`, `IBaseApiCallbackRequest`) from `@/interfaces` and utilize centralized helpers (`unwrapApiResponse`, `applyDataTransform`, `resolveQueryErrorNotification`, `resolveMutationNotifications`, `createSaveButtonProps`, `createFormFinishHandler`) from `@/utilities`.
- **[AVOID]** Multiple or fragmented handling strategies in custom hooks — Extract data from a single canonical source (`query.data?.data`), apply single-pass `useMemo` transform, and expose a single boolean for `isLoading`. Do not mutate internal Refine `result` objects.
- **[NEVER]** Mix single ID and batch ID parameters in mutation hooks without explicit batch typing — Keep `useCustomDelete` strictly single-item (`id: string | number` or `HandleCustomDeleteRequest<TData>`), preserving atomic and predictable mutation contracts.
- **[AVOID]** Using explicit type `any` in utility generic arguments and custom hook responses — Use strict generic constraints (`TData extends BaseRecord = BaseRecord`, `TVariables = Record<string, unknown>`, `unknown`) and inherit standard response interfaces (`IBaseApiQueryResponse`, `IBaseApiFormResponse`).
- **[AVOID]** Attaching redundant `queryOptions.select` wrapper functions in `useCustomDrawerForm` / `useCustomModalForm` when `initialValuesMapper` is not provided — Preserve the original `rest.queryOptions` pass-through to avoid allocating extra closures and dummy transforms on each render.
- **[AVOID]** Declaring pure utility helper functions (e.g. `getDefaultOptionValue`, `getDefaultOptionLabel`, `resolveRowKey`) locally inside custom hook files — Keep them organized in `@/utilities/api-hooks/` for reusability and clean separation of concerns.
- **[AVOID]** Coupling monolithic form field switch-case branches inside form modal components — Extract a dedicated generic field dispatcher (`CustomFormField`) into `@/components/common/forms/` with typed discriminated unions (`IFormField<TValues>`).
- **[PREFER]** Discriminated union sub-interfaces (`IInputFormField`, `INumberFormField`, `IPasswordFormField`, `ITextAreaFormField`, `ISelectFormField`, `ISwitchFormField`, `ICustomFormField`) over a single flat interface with optional mixed props for form schemas to guarantee compile-time type safety.
- **[PREFER]** Declarative CRUD container integration (`ListWrapper` with `table`, `filters`, `formModal` / `WrapperFormModal`) over manually stitching multiple standalone wrappers and passing boilerplate props in each page.
- **[AVOID]** Handling table query errors and retry callbacks at the outer container level (`ListWrapper`) — Delegate data table error rendering and retry mechanisms directly to `ListTable` via `tableQuery.error` and `getBackendErrorMessage`, keeping `ListWrapper` as a pure layout and coordination container.
- **[AVOID]** Monolithic interface files or retaining dead legacy contracts in `src/interfaces/` — Organize shared interfaces into single-responsibility modules (`auth`, `base-api`, `component`, `api-hooks`, `notification`, `media`, `navigation`, `filter`, `containers`, `forms`) with barrel export (`index.ts`), and prune unused types/interfaces during refactor cycles.
- **[PREFER]** Polymorphic form section schemas (`IFormSection` -> `card`, `plain`, `collapse`, `tabs`) inheriting from `IBaseFormSection` and coordinated via a single public entry point `CustomFormSection` over flat, unstructured form field arrays in `FormModalContainer`.
- **[NEVER]** Drop or unmount inactive tab panes in form tab sections — Always preserve form state with `destroyInactiveTabPane: false` (or `destroyOnHidden: false`) and `forceRender: true` so validation rules and state on inactive tabs remain intact upon submission.
- **[AVOID]** Rendering inline `CustomForm.Item` wrappers inside field dispatchers (`CustomFormField`) — Encapsulate each input widget into an atomic, dedicated custom form component in `src/components/common/forms/` (`CustomDatePickerForm`, `CustomHtmlEditorForm`, `CustomCodeEditorForm`, `CustomRadioGroupForm`, `CustomCheckboxGroupForm`, `CustomJsonToggleForm`).
- **[AVOID]** Merging header props (`title`, `description`, `icon`, `badge`) into base form section interfaces (`IBaseFormSection`) when sub-sections like `plain` or `tabs` do not use them — Segregate polymorphic form section interfaces (`ICardFormSection`, `ICollapseFormSection`, `IPlainFormSection`, `ITabsFormSection`) adhering to the Interface Segregation Principle (ISP) to ensure precise TypeScript IntelliSense.
- **[NEVER]** Rely on unverified `dataProvider.getApiUrl` method existence in custom data hooks without safe fallback (`getApiUrl?.() ?? ''`) — Data provider object instances might omit custom methods in certain runtime contexts.
- **[AVOID]** Conflating `getOne` query loading state (`queryResult.isLoading`) with create action in `useCustomModalForm` — When `action === 'create'`, `queryResult` is disabled (`enabled: false`), so `formLoading` should purely reflect `form.formLoading` or explicit mutation submission state.
- **[AVOID]** Monolithic schema metadata (`IFieldMetadata` / `*-field.constants.ts`) mixing table columns and form field definitions — Colocate table columns (`ColumnsType<T>`) and form fields (`IFormField<TValues>[]`) directly in page components, and encapsulate data table queries, search debounce, and modal forms in dedicated custom page hooks (`hooks/use*Page.ts`).
- **[AVOID]** Re-exporting shared domain types (e.g. `export type { IOption }`) across multiple interface files when canonically exported from `src/interfaces/component.ts`.
- **[PREFER]** Pure layout container pattern for `ListContainer` (`top`, `children`, `bottom` slots) with direct composition of `<ListTable />` and standalone `<FormModalContainer />` over nested prop passing (`table`, `formModal`, `customModals`).
- **[AVOID]** Declaring redundant type aliases (`ItemRecord = IItem`, `ImportItemRecord = IItem`, `ItemFormValues = IItemFormValues`) in page-level type files — Use canonical interface names (`IItem`, `IItemFormValues`) directly across components, table hooks, and modal forms to keep type contracts clean and unfragmented.
- **[PREFER]** Passing unified `table: UseCustomTableResponse<RecordType, TTransformed>` directly to `<ListTable />` over passing fragmented `tableProps` and `tableQuery` props separately.
- **[PREFER]** Shorthand `table.setFieldFilter(field, value)` with automatic operator resolution (`in` for array, `eq` for primitive), automatic page reset (`currentPage = 1`), and automatic empty-value cleanup over verbose manual `table.setFilters([{ field, operator: 'eq', value }])`.
- **[AVOID]** Treating valid falsy filter values (`false`, `0`) as empty when sanitizing or resetting table query filters — Only purge `undefined`, `null`, `""`, and empty arrays `[]`.
